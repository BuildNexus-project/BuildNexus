# Performance testing (SCRUM-45 / US-32)

A JMeter test plan that puts concurrent load on the two endpoints most likely
to be exercised by real traffic — project creation and design-document
upload — and measures response time and throughput. See
[RESULTS.md](RESULTS.md) for the numbers captured from the most recent run.

This is a tooling/on-demand story, not a CI gate: performance tests are
naturally longer-running than a unit or integration suite, and belong before
a release or when a regression is suspected — not on every push. Nothing
here runs in `ci.yml`.

## What the plan covers

`project-performance-test-plan.jmx` has two thread groups, each simulating
several users hitting one endpoint concurrently:

| Thread group | Endpoint under load | What each thread does |
|---|---|---|
| Project Creation Load | `POST /api/projects` | Registers and logs in as a Client (once), then loops `POST /api/projects` |
| Design Upload Load | `POST /api/designs/projects/{id}/documents` | Registers a Client and an Architect, creates a project, logs in as the seeded dev Admin to assign the Architect to it, then loops the multipart upload as that Architect |

Both endpoints require a valid BuildNexus JWT with a specific role (`Client`
for project creation, `Architect` — assigned to that project — for design
upload), so each thread mints its own test users through the real
`/api/auth/register` and `/api/auth/login` endpoints rather than using
fixture tokens; those setup calls are excluded from the per-endpoint results
in the report by simply reading the row for the sampler you care about, since
JMeter's aggregate stats are grouped by sampler name.

`fixtures/sample-design.pdf` is a minimal hand-built PDF (correct `%PDF-`
header, well under the 10 MB limit) — enough to pass `DesignFileValidator`'s
byte-sniffing without shipping a real design drawing into source control.

## Prerequisites

- A running BuildNexus environment — the local `docker compose` stack
  (`infra/docker-compose.yml`) is the default target and what
  [RESULTS.md](RESULTS.md) was captured against. Start it first:
  ```bash
  cd ../
  docker compose up -d
  ```
- [Apache JMeter](https://jmeter.apache.org/download_jmeter.cgi) 5.6+ on your
  machine. It is **not** vendored in this repository — the binary
  distribution is around 80 MB, and unlike the app services nothing here
  needs it packaged into a container. Unzip it and either put its `bin/`
  directory on `PATH`, or point `JMETER_CMD` at the executable directly
  (see below — `JMETER_CMD`, not `JMETER_BIN`, matters on Windows).

## Running it

```bash
cd infra/performance-tests
./run-performance-tests.sh
```

This runs the plan in non-GUI mode against `http://localhost:5000` (the
gateway's default local port) with the plan's default load — 20 concurrent
Client threads creating projects, 10 concurrent Architect threads uploading
designs — and writes:

- `results/results.jtl` — the raw sample-by-sample results
- `results/report/index.html` — JMeter's generated HTML dashboard (open it
  in a browser for charts, not just the numbers)

Both are git-ignored: they are regenerated by every run, and the numbers
that matter are transcribed into [RESULTS.md](RESULTS.md) after a run worth
keeping as a baseline.

### Pointing it elsewhere, or changing the load

Every knob is a JMeter property, passed straight through with `-J`:

```bash
# Against a deployed environment instead of localhost
./run-performance-tests.sh -Jprotocol=https -Jhost=buildnexus-gateway-2026.azurewebsites.net -Jport=443

# Heavier load
./run-performance-tests.sh -Jproject_threads=50 -Jproject_loops=20 -Jdesign_threads=25 -Jdesign_loops=10
```

| Property | Default | Meaning |
|---|---|---|
| `protocol` | `http` | Scheme for every request |
| `host` | `localhost` | Target host |
| `port` | `5000` | Target port (the gateway's default local port) |
| `admin_email` / `admin_password` | the local stack's seeded dev Admin | Used once per Design Upload thread, to assign the Architect to the project it just created — see `services/user-service/README.md` for where that seeded account comes from. Override these against an environment that seeds a different Admin. |
| `project_threads` / `project_rampup` / `project_loops` | `20` / `10` (seconds) / `10` | Concurrent Client users creating projects, and how many each creates |
| `design_threads` / `design_rampup` / `design_loops` | `10` / `10` (seconds) / `5` | Concurrent Architects uploading designs, and how many each uploads |

### On Windows

`JMETER_CMD` (not the more obvious `JMETER_BIN`) is deliberate:
`jmeter.bat` sets its own internal `JMETER_BIN` from its own location, but
only if one isn't already inherited from the environment — naming this
script's variable the same thing would leak in and point the launcher at the
wrong jar. If JMeter isn't on `PATH`:

```bash
JMETER_CMD="/c/path/to/apache-jmeter-5.6.3/bin/jmeter.bat" ./run-performance-tests.sh
```

## Re-running against a fresh environment

Every thread registers its own test users with unique, timestamped emails
(`jmeter.*.<run-id>@loadtest.invalid`), so the plan is safe to run again and
again against the same database without collisions. The test users and
projects it creates are not cleaned up afterwards — this is a
development/staging tool, and `docker compose down -v` (or, on Azure,
`terraform destroy` / `terraform apply` between demos — see
`../RUNBOOK.md`) already resets the database between sessions.
